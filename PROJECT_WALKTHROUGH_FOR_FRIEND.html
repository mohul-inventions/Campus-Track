🌟 What is CampusTrack?

CampusTrack is an end-to-end full-stack web application designed for university campuses to manage lost and found items. Instead of physical paper logs or informal chat groups, CampusTrack provides a centralized, secure platform backed by a normalized MySQL 8.0 relational database.

Key Highlights:
  • 3NF Normalized Relational Database (8 tables, strict Foreign Keys)
  • Deterministic 100-Point Matching Engine (Category, Location, Color, Brand, Date proximity)
  • ACID Transactions with Pessimistic Row Locking (SELECT ... FOR UPDATE) for claim approval
  • Automated AFTER UPDATE Database Triggers for immutable audit logging
  • 5 MySQL Stored Procedures & 3 Materialized Views

📐 System Architecture

  • Frontend: React 18 SPA built with Vite, styled using Tailwind CSS (dark obsidian theme with gold accents), responsive navbar, sidebar, and status pipelines. Hosted on Vercel.
  • Backend: Node.js & Express REST API with JWT authentication, bcrypt password hashing, and MySQL connection pooling.
  • Database: MySQL 8.0 with InnoDB engine, complete normalization (3NF), views, stored procedures, and triggers.

🎯 100-Point Rule-Based Matching Algorithm

When an item is reported, the backend evaluates all opposite active reports using a weighted formula:

Attribute Weight Rule
Category Match25 ptsExact category ID equality
Location Match25 ptsExact campus building/location equality
Color Match15 ptsCase-insensitive color or substring match
Brand Match15 ptsCase-insensitive brand string equality
Description Match10 ptsKeyword overlap in item title and notes
Date Proximity10 ptsWithin 3 days: 10 pts; within 7 days: 6 pts; within 14 days: 3 pts

Total: 100 points. Scores ≥ 50% are suggested to users, and scores ≥ 80% mark candidate items as Matched.

🛡️ Faculty Viva Q&A Cheat Sheet

Q1: How is your database normalized?

Ans: The schema satisfies Third Normal Form (3NF). All columns are atomic (1NF), all non-key fields depend entirely on the primary key (2NF), and transitive dependencies have been removed by isolating lookup entities like categories and locations into their own tables referenced by foreign keys (3NF).

Q2: Why are transactions essential in this project?

Ans: Approving a claim involves updating three separate tables (claims, found_items, lost_items) and writing an audit log. Without transactions, a crash midway would leave data inconsistent (e.g. found item claimed, but lost item still marked lost). Our ACID transaction uses START TRANSACTION and pessimistic row locking (SELECT ... FOR UPDATE) to guarantee atomic execution and prevent race conditions.

Q3: What do the database triggers do?

Ans: We implemented AFTER UPDATE triggers on lost_items, found_items, and claims. Any time a status changes, the trigger automatically records the old status, new status, timestamp, and user ID into status_audit_log, creating an immutable audit trail at the database engine level.
